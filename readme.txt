LLM games

This readme is the shared machinery for making and playing games. It is enough
to begin without the original checkout. Keep instructions in ordinary language;
agents work out how to use available tools. No command recipes, launcher scripts
or required metadata formats. Each game's rules live in game; its files are its
memory. Carry this readme with each new game so it can travel independently.

Find your bearings

Follow the user's request: discuss, inspect, create, change, run or continue.
Being in a directory does not appoint you a player or authorize starting play.
If game exists, read it and the relevant recorded state. If there is no game
and no recorded play, help develop one when asked. Missing rules amid existing
rounds, conflicting instructions or several possible target games need attention;
do not invent a continuation. If the purpose, target or a role needed for play
is unclear, inspect what you can, then ask the user or whoever is arranging play.

Discussion, inspection and construction are different from participation. A
game's stop and play boundaries do not prevent helping the user understand it
or creating another game elsewhere. If already responsible for running play,
make any interruption or handoff explicit rather than silently abandoning it.

Make or change a game

Develop the idea through conversation. Follow what the user already knows;
offer sensible defaults and ask only what matters. Establish the task, players,
leader, round activities and ending. Put the rules and needed context in game,
including the original prompt and participant choices where they read naturally.
Leave unresolved choices clear; never invent a supplied task or pretend setup
is complete. There is no questionnaire or required form.

Use a fresh named directory in the requested location. Without a chosen location,
use a sibling of an existing game, or games/ beside this readme when no game is
present. Preserve existing directories. Write game and copy this readme there;
use relative game paths. Creating a sibling does not resume or alter the source.
An unstarted game may be edited when requested. Once play begins, preserve its
history; put new direction in later instructions or make a fresh game.

Modules are optional prose additions. When requested and available, read their
text and include it in labeled sections of game. They may be in modules/ in a
machinery checkout or already included in a game being adapted. Keep those
included instructions with the game. If a requested module is unavailable, say
so; use the requested behavior when clear, otherwise ask. Do not claim to have
loaded missing text. This readme alone supports creation without any modules.

Save without starting unless play is requested. When ready and asked to start,
the leader writes the first round-start last. Replays use a fresh directory and
starting instructions, never old rounds, logs, reports or stop files.

Arrange play

Start with an interactive leader managing non-interactive players. Give each
participant its game directory, instructions, initial role and a distinct
single-word name unused as a filename. Reuse a returning participant's identity;
otherwise use the supplied name or choose one. Only one instance may act as each
participant at a time. The leader plays only if the game says so.

When asked to run, discover how to bring in the requested players using what is
available here. Use existing authentication outside the game. Explain unavailable
choices rather than silently replacing an agent or model. Ask only for what is
missing; do not start dependent work while an essential choice remains unclear.

Keep the interactive session active and follow the files to see what is due.
Bring participants back when they have more to do, including within a round.
Check deadlines even without file changes. A finished invocation is not proof
of a completed move. Honor stop and surface failures needing attention. If the
session ends, someone must resume arranging turns; play does not run itself.

Taking part

Use your assigned role and read game. On every invocation or check, look for
stop anywhere within this game, read your own log if it exists and the latest
round-results, then the relevant round instructions and submissions. Follow
recorded leadership transfers before acting, even if you already submitted.

Do only the work currently due. Publish complete submissions in the named files;
an existing submission is not permission to overwrite it or submit twice. If
nothing is due or a prerequisite is missing, a non-interactive participant logs
that and exits. The session arranging play brings them back. Expected waiting
is not failure. If you cannot tell what is due or the state is inconsistent,
record the issue and seek clarification rather than guessing or taking over.

Append actions, including reads and outside influences, to your own log, the
file of your name. Prefix lines with the round number, or - before play. Never
write another participant's log. Files must suffice without private conversation
history. Stay within the game for play unless the user or game authorizes wider
scope. Assume good faith unless the game says otherwise.

Rounds

Numbered subdirectories hold rounds, one open at a time. The leader opens one
with round-start: who may play, what to submit, the filenames and when it ends.
The leader closes it by renaming round-start to round-end, then writes
round-results: the outcome, next action and next leader. If no successor is
named, the leader stays. If a successor does not act, wait; nobody silently
takes over. The initial interactive session still arranges turns, including
for the new leader, without retaining the old game role.

After play begins, preserve written files. Only your own log may be appended
to, and the leader may rename round-start to round-end. Publish corrections as
new instructions or work when authorized by the game, never rewritten history.

Stop and continuation

A stop anywhere within this game halts its play: participants log seeing it and
do no more game work. An early stop is not permission to finish submissions or
reports. It does not prevent requested discussion, inspection or a new game
elsewhere. At normal completion, the leader records the outcome, finishes and
checks any required outputs, then creates stop. Reporting is a game choice.

When asked to continue, use the recorded state. Resolve the reason for a stop
before clearing it as part of an authorized resumption. If it is unclear whether
the user means resume, extend or replay, ask. Completed play does not silently
restart. Check existing work before repeating an interrupted action; if a step
is still being finished, wait. Unexplained gaps need clarification. Never erase
history or replace an existing game's protocol copy just to make it proceed.

Tell the user where things stand, what happens next, and anything needed from
them. Be clear whether a game is saved, running, waiting, stopped or finished.
